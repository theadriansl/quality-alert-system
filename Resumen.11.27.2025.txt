✅ 2. BUG CRÍTICO: USUARIO NO SE GUARDABA EN LOCALSTORAGE
----------------------------------------------------------
**Problema:**
Al navegar de Dashboard a 8D Workflow, el usuario se perdía, causando:
- localStorage.getItem('user') → null
- currentUserId → undefined
- Todas las secciones bloqueadas para todos los usuarios

**Causa Raíz:**
En `/frontend/src/context/AuthContext.js`:
- Función login() guardaba el token: `localStorage.setItem('token', token)`
- Pero NO guardaba el usuario: solo hacía `setUser(user)` en React state
- 8DWorkflow.js intentaba leer: `JSON.parse(localStorage.getItem('user'))`
- Resultado: null → bloqueo total

**Solución Implementada:**

A) AuthContext.js - Función login (línea 46):
   ANTES:
   ```javascript
   localStorage.setItem('token', token);
   setUser(user);
   ```

   DESPUÉS:
   ```javascript
   localStorage.setItem('token', token);
   localStorage.setItem('user', JSON.stringify(user));  // ← AÑADIDO
   setUser(user);
   ```

B) AuthContext.js - Función logout (línea 58):
   ANTES:
   ```javascript
   localStorage.removeItem('token');
   ```

   DESPUÉS:
   ```javascript
   localStorage.removeItem('token');
   localStorage.removeItem('user');  // ← AÑADIDO
   ```

**Estado:** ✅ FUNCIONANDO CORRECTAMENTE

✅ 3. BUG CRÍTICO: ESCALATIONPATH NO LLEGABA A 8DWORKFLOW
----------------------------------------------------------
**Problema:**
workflowData.escalationPath era undefined, causando:
- hasPath → false
- countermeasure_users → []
- D3-MFG bloqueado incluso para usuarios autorizados

**Causa Raíz - Múltiple:**

A) Backend retorna escalationPath en camelCase:
   - transformToCamelCase convierte: escalation_path → escalationPath (columna)
   - Pero el CONTENIDO del JSONB NO se transforma recursivamente
   - JSONB almacena: {issue_users: [...], countermeasure_users: [...]}

B) Frontend service mapeaba mal (eightDService.js):
   - Línea 453 retornaba: `escalation_path: escalationPath`
   - Pero 8DWorkflow.js buscaba: `workflowData.escalationPath` (camelCase)
   - Resultado: undefined

**Solución Implementada:**

A) eightDService.js - Mapeo de escalationPath (líneas 310-314):
   ```javascript
   const escalationPath = report.escalationPath ? {
     issue_users: report.escalationPath.issue_users ||
                  report.escalationPath.issueUsers || [],
     countermeasure_users: report.escalationPath.countermeasure_users ||
                           report.escalationPath.countermeasureUsers || [],
     confirmation_users: report.escalationPath.confirmation_users ||
                         report.escalationPath.confirmationUsers || []
   } : null;
   ```

B) eightDService.js - Return object (líneas 453-454):
   ```javascript
   escalation_path: escalationPath,  // Para TeamAssignmentTab (usa snake_case)
   escalationPath: escalationPath,   // Para 8DWorkflow (usa camelCase)
   ```

C) 8DWorkflow.js - Blocking logic (líneas 124-140):
   ```javascript
   const isCountermeasureResponsible = () => {
     if (!currentUser?.id || !workflowData?.escalationPath) {
       return false;
     }
     const countermeasureUsers = workflowData.escalationPath.countermeasure_users || [];
     return countermeasureUsers.includes(currentUser.id);
   };

   const isD3MFGBlocked = !isD123Approved || (!isCountermeasureResponsible() && !isAdmin);
   ```

FLUJO DE APROBACIÓN SECUENCIAL D1-D2-D3
================================================================================

1. EMISOR crea reporte → Status: draft
2. EMISOR envía a aprobación → POST /8d/reports/:id/submit
   * Status cambia a: pending_approval_1
   * Se registra en audit log

3. APROBADOR 1 revisa:
   * Aprobar: POST /8d/reports/:id/approve-step-1
     - Status → pending_approval_2
     - Se registra aprobación en audit log
   * Rechazar: POST /8d/reports/:id/reject-step-1
     - Status → draft (regresa a Emisor)
     - Se registra rechazo en audit log

4. APROBADOR 2 revisa:
   * Aprobar: POST /8d/reports/:id/approve-step-2
     - Status → pending_approval_3
     - Se registra aprobación en audit log
   * Rechazar: POST /8d/reports/:id/reject-step-2
     - Status → pending_approval_1 (regresa a A1)
     - Se registra rechazo en audit log

5. APROBADOR 3 revisa (FINAL):
   * Aprobar: POST /8d/reports/:id/approve-step-3
     - Status → approved
     - Se registra aprobación en audit log
     - ✅ DESBLOQUEA D4-D8 para edición
   * Rechazar: POST /8d/reports/:id/reject-step-3
     - Status → pending_approval_2 (regresa a A2)
     - Se registra rechazo en audit log
