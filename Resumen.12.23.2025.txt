## 1. SOLICITUDES PRINCIPALES DEL USUARIO

### Solicitud #1: Permitir edición de D2 (Partes) y D3 (Contención) post-aprobación
**Contexto**: Una vez que D1-D2-D3 ha sido aprobada, se necesita poder editar:
- D2: Sección de "Cliente, Proyecto y Números de Parte" (pueden descubrirse nuevas partes afectadas)
- D3: Toda la sección de Contención (costos de retrabajo pueden cambiar durante investigación)

**Justificación**: "para que no sea tanto rollo editar esos campos que no afectan al flujo de solución del problema"

**Requisitos UI/UX**:
- Botones "Editar" y "Guardar" para cada sección
- Botones duplicados arriba y abajo (para evitar scroll)
- Toast notifications (verde auto-hide para éxito, rojo manual-close para errores)
- No afectar el estatus de aprobación de D1-D2-D3

### Solicitud #2: Remover bloqueo de D4 para acceder a D5
**Contexto**: "Quita el bloque de usuario de que necesita aprobación de D4 para hacer D5, en ocasiones la contramedida temporal es la misma que la permanente, lo puede ir haciendo Draft si no"

**Requisito**:
- D5 debe desbloquearse cuando D1-D2-D3 esté aprobada
- NO necesita esperar a que D4 esté completada
- Usuario puede trabajar D4 y D5 en paralelo como borradores

**Causa**: Al remover el condicional `{hasD4RootCauses && (`, se cambió el `)}` por `</div>` creando una etiqueta de cierre extra.


### Error #2: D5 bloqueado después de guardar D2/D3
**Síntoma**: Al editar partes o D3, el sistema pensaba que D1-D2-D3 ya no estaba aprobada.

**Causa**: `onDataUpdate` recibía todo el objeto del reporte y sobrescribía `d1D2D3ApprovalStatus`.

**Solución**: Modificar TeamAssignmentTab.js para enviar SOLO los campos modificados (ver sección 3.5).

**Verificación**:
- Campo `d1D2D3ApprovalStatus` debe permanecer como 'approved'
- Variable `isD123Approved` en 8DWorkflow.js debe seguir siendo `true`
- Tabs D4 y D5 deben permanecer desbloqueadas

### Error #3: D5 bloqueado por falta de D4 completada
**Síntoma**: Usuario no podía acceder a D5 desde D4.

**Causa**: Lógica de bloqueo verificaba `!workflowData?.d4Completed`.

**Solución**: Cambiar a `!isD123Approved` (igual que D4).

**Clarificación del Usuario**:
"es que cuando se guardo D1, D2 y D3 tambien penso que no esta aprobada, no debia cambiar ese estatus en D1 D2 D3"
"si debe estar bloqueado si no ha enviado a aprobacion, pero si ya envio a aprobacion debe desbloquearse"

## 6. FLUJO COMPLETO DE EDICIÓN POST-APROBACIÓN

### Escenario: Usuario edita partes en D2

1. **Estado Inicial**:
   - D1-D2-D3 está aprobada (d1_d2_d3_approval_status = 'approved')
   - Campo fieldsLocked = true en TeamAssignmentTab
   - Botón "✏️ Editar Partes Afectadas" visible

2. **Usuario hace clic en "Editar"**:
   - setIsEditingParts(true)
   - Campos de partes se habilitan: disabled={fieldsLocked && !isEditingParts} → false
   - Botón cambia a "💾 Guardar Cambios en Partes"

3. **Usuario modifica cantidades** (ej: qtyInTransit, qtyWithCustomer)

4. **Usuario hace clic en "Guardar"**:
   - handleSavePartsChanges() se ejecuta
   - setIsSavingPartialChanges(true)
   - Botón muestra "⏳ Guardando..."

5. **Request al Backend**:
   ```
   PUT /8d/reports/4/update-parts
   Headers: { Authorization: Bearer token }
   Body: {
     selectedClient: { id: 1, name: "Faurecia..." },
     selectedProject: { id: 9, projectNumber: "PROJ-FAU-2024-001", ... },
     selectedParts: [ {...}, {...}, ... ]
   }
   ```

6. **Backend procesa** (eightDEndpoints.updatePartsOnly):
   - Verifica que reporte existe
   - DELETE FROM eightd_parts WHERE report_id = 4
   - INSERT nuevas partes (3 partes en el ejemplo)
   - UPDATE eightd_reports SET updated_at = NOW()
   - COMMIT
   - Retorna reporte completo con partes

7. **Audit Middleware**:
   - Captura BEFORE state (partes antes del cambio)
   - Captura AFTER state (partes después del cambio)
   - Detecta cambio: hasPartsChanged(before, after) = true
   - Crea log: "Partes afectadas actualizadas (Cliente, Proyecto, Números de Parte)"

8. **Frontend recibe respuesta**:
   - result.success = true
   - showToast('success', '✅ Partes afectadas actualizadas correctamente')
   - setIsEditingParts(false)
   - Actualiza estados locales: setSelectedClient, setSelectedProject, setSelectedParts
   - Llama onDataUpdate con SOLO los campos modificados:
     ```javascript
     onDataUpdate({
       selectedClient: {...},
       selectedProject: {...},
       selectedParts: [...]
     })
     ```

9. **8DWorkflow.js recibe actualización** (handleDataUpdate):
   ```javascript
   const updatedData = { ...workflowData, ...data };
   // workflowData tiene d1D2D3ApprovalStatus = 'approved'
   // data solo tiene selectedClient, selectedProject, selectedParts
   // updatedData preserva d1D2D3ApprovalStatus = 'approved' ✅
   setWorkflowData(updatedData);
   ```

10. **Toast notification**:
    - Aparece en centro de pantalla, fondo verde
    - "✅ Partes afectadas actualizadas correctamente"
    - Auto-desaparece en 3 segundos

11. **Estado Final**:
    - Partes actualizadas en BD y frontend
    - d1D2D3ApprovalStatus sigue siendo 'approved' ✅
    - D4 y D5 siguen desbloqueadas ✅
    - Campos vuelven a estado locked
    - Botón vuelve a "✏️ Editar Partes Afectadas"

### Escenario: Usuario edita D3 (Contención)

- Payload: { d3Data: {...} }

## 13. PREGUNTAS FRECUENTES (FAQ)

### P: ¿Por qué las partes están en una tabla separada?
**R**: Diseño normalizado. Un reporte puede tener múltiples partes afectadas (relación 1-a-muchos).

### P: ¿Por qué D3 no se guarda como JSON si tiene múltiples campos?
**R**: Decisión de diseño original. D3 tiene campos que se consultan individualmente en reportes, por lo que se guardaron como columnas separadas para mejor queryabilidad.

### P: ¿Puedo agregar más campos editables a D2 o D3?
**R**: Sí, pero solo agrega campos que NO afecten el flujo de solución del problema. Actualmente:
- D2: Solo Cliente, Proyecto, Números de Parte
- D3: Toda la sección (detección, disposición, costos de retrabajo)

### P: ¿Qué pasa si dos usuarios editan al mismo tiempo?
**R**: El último en guardar sobrescribe. No hay lock optimista implementado. Considerar agregar `version` field si es problema.

### P: ¿Se puede editar D4, D5, etc. post-aprobación?
**R**: NO implementado en esta sesión. Actualmente solo D2 (partes) y D3 (contención). Si se necesita, seguir el mismo patrón.

### P: ¿Los cambios parciales afectan el workflow de aprobación?
**R**: NO. Los campos de estado de aprobación NO se modifican. Solo se actualizan los datos técnicos y el timestamp.

### P: ¿Se registra quién hizo el cambio parcial?
**R**: SÍ. Audit middleware captura user_id, user_name, old_value, new_value para cada cambio.
