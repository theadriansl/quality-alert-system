7. CORRECCION DE ERRORES
--------------------------------------------------------------------------------
[COMPLETADO] Error 404 en actualizacion de usuarios
   Problema: Ruta PUT /users/:id no existia
   Causa: Endpoint no registrado en server.js
   Solucion: Agregada ruta en linea 117
   Estado: RESUELTO

[COMPLETADO] Error 500 - Parameter numbering
   Problema: SQL parameter $11 no existia, saltaba de $10 a $12
   Causa: paramCount++ innecesario para updated_at = CURRENT_TIMESTAMP
   Error: "could not determine data type of parameter $11"
   Solucion:
   - Removido paramCount++ antes de push de updated_at
   - updated_at no necesita parametro ($N)
   - Ahora numeracion es correcta: $1 a $10 + $11 para userId
   Archivo: backend/endpoints/usersEndpoints.js linea 157-158
   Estado: RESUELTO

[COMPLETADO] Error 500 - Invalid input syntax for integer
   Problema: PostgreSQL rechazaba empty string ("") para campo INTEGER
   Error: "invalid input syntax for type integer: ''"
   Causa: Frontend enviaba managerId = "" cuando estaba vacio
   PostgreSQL espera: integer o NULL, NO string vacio

   Solucion implementada:
   - Validacion en updateUser antes de insertar en values array
   - Conversion de empty strings a NULL para campos integer
   - Codigo agregado (lineas 147-151):
     ```javascript
     let value = snakeData[key];
     if ((key === 'manager_id' || key === 'hierarchy_level') && value === '') {
       value = null;
     }
     values.push(value);
     ```
   - Aplica a: manager_id, hierarchy_level
   - NULL es aceptado por PostgreSQL para campos INTEGER nullable
   Archivo: backend/endpoints/usersEndpoints.js
   Estado: RESUELTO

[COMPLETADO] Datos incorrectos del Quality Director
   Problema: Usuario tenia "Quality" como first_name, "Director" como last_name
   Causa: Script de poblacion inicial uso titulos en lugar de nombres
   Solucion:
   - Actualizado via SQL directo a nombres reales:
     * first_name: "Juan"
     * last_name: "Gonzalez"
     * position: "Quality Director"
     * role: "champion"
   Estado: RESUELTO

[COMPLETADO] Usuario no podia editar nombres
   Problema: Campo name no editable en formulario
   Causa: handleEdit intentaba split de user.name que no existia
   Solucion:
   - loadUsers normaliza firstName/lastName a 'name'
   - handleEdit usa firstName/lastName directamente
   Estado: RESUELTO

[COMPLETADO] Warning: Formato de fecha incorrecto
   Problema: Input type="date" recibia "2025-09-30T06:00:00.000Z"
   Error: "The specified value does not conform to the required format, yyyy-MM-dd"
   Causa: Fechas ISO completas con timestamp en inputs type="date"

   Solucion implementada:
   - Agregada funcion formatDateForInput() (lineas 43-52)
   - Convierte fecha ISO a formato "yyyy-MM-dd"
   - Aplicada en handleEditProject:
     * startDate: formatDateForInput(project.startDate)
     * targetEndDate: formatDateForInput(project.targetEndDate)
   Archivo: frontend/src/pages/ClientDetail.js
   Estado: RESUELTO - 0 warnings

[COMPLETADO] Mensaje engañoso "Datos MOCK cargados"
   Problema: Console mostraba "Datos MOCK cargados (no backend)"
   Causa: Logica incorrecta verificaba si email contenia '@8dsystem.com'
   Realidad: Usuarios SI estaban en PostgreSQL, mensaje era falso

   Solucion:

NOTAS TECNICAS IMPORTANTES - SESION 2
================================================================================

1. MANEJO DE NULL vs EMPTY STRING
   PostgreSQL:
   - Campos INTEGER NO aceptan empty string ("")
   - Campos INTEGER aceptan NULL
   - VARCHAR acepta tanto "" como NULL

   Solucion implementada:
   - Validacion en backend antes de query
   - Conversion de "" a NULL para campos: manager_id, hierarchy_level
   - Se aplica en updateUser() lineas 147-151

2. ESTRUCTURA DE JERARQUIA
   Diseno:
   - manager_id es FK a users.id con ON DELETE SET NULL
   - Permite estructura recursiva (managers de managers)
   - hierarchy_level facilita queries y filtros
   - NULL en manager_id = top level (Director/CEO)

   Ventajas:
   - Facil filtrar por nivel jerarquico
   - Facil obtener subordinados de un manager
   - Facil validar que manager sea de nivel superior
   - Indices optimizan queries

3. FILTRADO DE MANAGERS EN FRONTEND
   Logica implementada:
   - Excluir usuario actual (no reportar a si mismo)
   - Solo mostrar usuarios con hierarchy_level menor (superior)
   - Ordenar por nivel (Directores primero, luego Managers, etc)
   - Formato legible con posicion y nivel

4. TRANSFORMACION BIDIRECCIONAL
   Frontend -> Backend (request):
   - managerId -> manager_id
   - hierarchyLevel -> hierarchy_level
   - firstName -> first_name

   Backend -> Frontend (response):
   - manager_id -> managerId
   - hierarchy_level -> hierarchyLevel
   - first_name -> firstName

   Utilidad: transformToSnakeCase / transformToCamelCase

5. CASCADAS Y RELACIONES
   manager_id:
   - ON DELETE SET NULL (no elimina usuarios subordinados)
   - Si se elimina manager, subordinados quedan sin manager
   - Permite reorganizacion de estructura

6. DEPARTAMENTOS DINAMICOS
   Implementacion:
   - Input type="text" con list="departments-list"
   - Datalist contiene opciones existentes
   - Usuario puede escribir libremente
   - getUniqueDepartments() obtiene lista actual de DB
   - Sin necesidad de modificar codigo para agregar departamentos

7. FORMATO DE FECHAS
   Problema:
   - Inputs type="date" requieren formato "yyyy-MM-dd"
   - Backend retorna ISO 8601: "2025-09-30T06:00:00.000Z"

   Solucion:
   - Funcion formatDateForInput() convierte ISO a yyyy-MM-dd
   - Usa date.toISOString().split('T')[0]
   - Aplicada cuando se cargan datos para edicion

8. LOGICA CLIENTE vs PROVEEDOR
   Distincion:
   - Cliente: Tiene vendor_number (nos emite 8D)
   - Proveedor: NO tiene vendor_number (le emitimos 8D)

   Ventaja:
   - Misma tabla (clients) para ambos
   - Distincion simple via campo nullable
   - Estadisticas separadas facilmente
