### PROBLEMA 1: "Responsable Principal" mostraba persona incorrecta
**Síntoma**: La tabla mostraba a John Quality (Primary/D1 worker) en vez de
Adrian Salazar (Emisor/Creador del reporte)

**Causa Raíz**:
- getIssueSection() usaba escalation_path.issue_users[0] como Primary
- Este valor podía ser editado manualmente y no siempre era el creador

**Solución**:
- Modificado getIssueSection() para SIEMPRE usar data.createdBy como Primary
- Modificado 8DWorkflow.js para siempre poner creador primero en issue_users
- Agregado createdBy al return de eightDService.js

**Archivo**: TeamAssignmentTab.js (líneas 404-435)
```javascript
const getIssueSection = () => {
  const creatorUser = findUserById(data.createdBy);
  return {
    primary: creatorUser || null,  // Siempre el creador
    approvers: [...]
  };
};
```

quién estaba logeado

### PROBLEMA 3: Campos no se bloqueaban inmediatamente tras enviar a aprobación
**Síntoma**: Después de hacer clic en "Enviar a Aprobación", los campos D1-D2-D3
seguían editables hasta hacer refresh de la página

**Causa Raíz**:
- handleSave() actualizaba backend pero no actualizaba el estado local de React
- fieldsLocked dependía de data.d1D2D3ApprovalStatus que no se actualizaba

**Solución**:
- Agregado setD123ApprovalStatus('pending_approval_1') después de API call
- Agregado setCurrentApprovalStep(1)
- Llamado onDataUpdate() para notificar al componente padre

**Archivo**: TeamAssignmentTab.js (líneas 1673-1687)
```javascript
setD123ApprovalStatus('pending_approval_1');
setCurrentApprovalStep(1);
if (onDataUpdate) {
  onDataUpdate({
    ...data,
    d1D2D3ApprovalStatus: 'pending_approval_1',
    currentApprovalStep: 1
  });
}
```

### PROBLEMA 4: Lógica de bloqueo no manejaba estados específicos del flujo secuencial
**Síntoma**: Los campos no se bloqueaban correctamente según el rol del usuario
y el estado actual del reporte

**Estados del Sistema NUEVO**:
- draft: Solo creador puede editar
- pending_approval_1/2/3: NADIE puede editar (solo aprobar/rechazar)
- rejected_by_a1/a2/a3: Solo creador puede editar
- approved: NADIE puede editar

**Solución**:
- Actualizado isD123Locked() para manejar estados específicos:
  * pending_approval_X → Bloqueado para TODOS
  * rejected_by_aX → Bloqueado para todos EXCEPTO el creador
  * approved → Bloqueado para TODOS
  * Excepción: Admins SIEMPRE pueden editar

**Archivo**: TeamAssignmentTab.js (líneas 121-187)
```javascript
if (approvalStatus === 'pending_approval_1' ||
    approvalStatus === 'pending_approval_2' ||
    approvalStatus === 'pending_approval_3') {
  return true; // Bloqueado para todos durante aprobación
}

if (approvalStatus === 'rejected_by_a1' ||
    approvalStatus === 'rejected_by_a2' ||
    approvalStatus === 'rejected_by_a3') {
  return !isCreator; // Solo el creador puede editar
}
```

**User Story validada**:
✅ Robert Robert rechaza → Campos bloqueados para Robert (read-only)
✅ Adrian Salazar (creador) puede editar después del rechazo
✅ Administradores pueden editar en cualquier momento

### PROBLEMA 5: Aprobadores podían cambiar su propio campo durante revisión
**Síntoma**: Cuando Aprobador 1 estaba revisando, podía cambiar su propio
nombre en la lista de aprobadores, o cambiar a aprobadores anteriores

**Regla de Negocio**:
- Aprobador 1: Solo puede modificar Aprobador 2 y 3 (no a sí mismo)
- Aprobador 2: Solo puede modificar Aprobador 3 (no a 1 ni a sí mismo)
- Aprobador 3: No puede modificar a nadie (todos bloqueados)

**Solución**:
- Creada función isApproverFieldLocked(approverIndex)
- Lógica: Bloquear si currentApprovalStep >= (approverIndex + 1)
- Aplicado a cada campo de aprobador individualmente

**Archivo**: TeamAssignmentTab.js (líneas 173-187, 2145-2171)
```javascript
const isApproverFieldLocked = (approverIndex) => {
  if (fieldsLocked) return true;
  if (!currentApprovalStep || currentApprovalStep === 0) return false;
  return currentApprovalStep >= (approverIndex + 1);
};

// En el render:
<UserSearchCell disabled={isApproverFieldLocked(0)} /> // Aprobador 1
<UserSearchCell disabled={isApproverFieldLocked(1)} /> // Aprobador 2
<UserSearchCell disabled={isApproverFieldLocked(2)} /> // Aprobador 3
```

**Matriz de Bloqueo**:
| Estado           | Aprobador 1 | Aprobador 2 | Aprobador 3 |
|------------------|-------------|-------------|-------------|
| pending_approval_1 | 🔒 LOCKED   | 🔓 UNLOCKED | 🔓 UNLOCKED |
| pending_approval_2 | 🔒 LOCKED   | 🔒 LOCKED   | 🔓 UNLOCKED |
| pending_approval_3 | 🔒 LOCKED   | 🔒 LOCKED   | 🔒 LOCKED   |

### PROBLEMA 6: Doble-clic causaba error en rechazo
**Síntoma**: Al rechazar, primero aparecía mensaje de éxito ✅, luego mensaje
de error ❌ "Error al rechazar. Por favor intenta de nuevo."

**Causa Raíz**:
- Usuario hacía doble-clic accidental en botón "Confirmar Rechazo"
- Primera llamada: Éxito (cambia step de 1 a 0)
- Segunda llamada: Falla (ya está en step 0)

**Solución**:
- Agregado verificación if (loading) return en handleSubmit()
- Agregado e.stopPropagation() para prevenir propagación
- Agregado console.log para detectar intentos duplicados

**Archivo**: ApprovalModal.js (líneas 27-62)
```javascript
const handleSubmit = async (e) => {
  e.preventDefault();
  e.stopPropagation();

  if (loading) {
    console.log('⚠️ Ya hay una operación en proceso, ignorando clic duplicado');
    return;
  }

  setLoading(true);
  // ... resto del código
};
```

### PROBLEMA 7: Aprobador veía botones después de rechazar
**Síntoma**: Robert Robert rechazaba el reporte, navegaba al historial, y
al regresar seguía viendo los botones de "Aprobar/Rechazar"

**Causa Raíz**:
- Endpoint /8d/reports/:id/approval-status usaba sistema VIEJO
- No reconocía estados del sistema NUEVO (rejected_by_a1, etc.)
- Siempre retornaba pending_approver aunque el reporte estuviera rechazado

**Solución**:
- Actualizado getApprovalStatus() para soportar AMBOS sistemas:
  * Sistema NUEVO: d1_d2_d3_approval_status
  * Sistema VIEJO: status (para compatibilidad con otros módulos)
- pending_approver = null cuando estado es rejected_by_aX o approved
- Solo retorna pending_approver cuando estado es pending_approval_X

**Archivo**: approvalsEndpoints.js (líneas 386-499)
```javascript
// Sistema NUEVO
if (report.d1_d2_d3_approval_status) {
  const d123Status = report.d1_d2_d3_approval_status;

  // Solo pending_approver si está en pending_approval_X
  if (d123Status === 'pending_approval_1' ||
      d123Status === 'pending_approval_2' ||
      d123Status === 'pending_approval_3') {
    // Obtener aprobador desde escalation_path
    pendingApprover = { ... };
  }
  // Si rejected_by_aX o approved → pendingApprover = null
}
```

**Resultado**:
✅ Cuando estado = rejected_by_a1 → pendingApprover = null
✅ ApprovalPanel no muestra botones si pendingApprover es null
✅ Robert NO ve botones después de rechazar

## 4. ARQUITECTURA DEL SISTEMA DE APROBACIÓN SECUENCIAL
================================================================================

### Estados del Sistema (d1_d2_d3_approval_status)

```
draft
  ↓ (Emisor envía)
pending_approval_1
  ↓ (Aprobador 1)
  ├→ approved → pending_approval_2
  └→ rejected → rejected_by_a1 → draft (Emisor corrige)

pending_approval_2
  ↓ (Aprobador 2)
  ├→ approved → pending_approval_3
  └→ rejected → rejected_by_a2 → draft

pending_approval_3
  ↓ (Aprobador 3)
  ├→ approved → approved (FIN)
  └→ rejected → rejected_by_a3 → draft
```

### Campos de Aprobación (base de datos)

| Campo                    | Tipo      | Descripción                           |
|--------------------------|-----------|---------------------------------------|
| d1_d2_d3_approval_status | VARCHAR   | Estado general del flujo              |
| current_approval_step    | INTEGER   | 0=draft, 1-3=aprobadores              |
| approval_1_status        | VARCHAR   | 'pending','approved','rejected'       |
| approval_1_by            | INTEGER   | ID del Aprobador 1                    |
| approval_1_at            | TIMESTAMP | Fecha/hora de decisión                |
| approval_1_comments      | TEXT      | Comentarios (obligatorios si rechaza) |
| approval_2_status        | VARCHAR   | Similar para Aprobador 2              |
| approval_2_by            | INTEGER   |                                       |
| approval_2_at            | TIMESTAMP |                                       |
| approval_2_comments      | TEXT      |                                       |
| approval_3_status        | VARCHAR   | Similar para Aprobador 3              |
| approval_3_by            | INTEGER   |                                       |
| approval_3_at            | TIMESTAMP |                                       |
| approval_3_comments      | TEXT      |                                       |

### Permisos por Rol

| Estado           | Emisor  | Aprobador 1 | Aprobador 2 | Aprobador 3 | Admin |
|------------------|---------|-------------|-------------|-------------|-------|
| draft            | ✏️ Editar | 👁️ Ver      | 👁️ Ver      | 👁️ Ver      | ✏️ Editar |
| pending_approval_1 | 👁️ Ver | ✅❌ A/R   | 👁️ Ver      | 👁️ Ver      | ✏️ Editar |
| pending_approval_2 | 👁️ Ver | 👁️ Ver     | ✅❌ A/R    | 👁️ Ver      | ✏️ Editar |
| pending_approval_3 | 👁️ Ver | 👁️ Ver     | 👁️ Ver     | ✅❌ A/R    | ✏️ Editar |
| rejected_by_aX   | ✏️ Editar | 👁️ Ver    | 👁️ Ver      | 👁️ Ver      | ✏️ Editar |
| approved         | 👁️ Ver | 👁️ Ver     | 👁️ Ver      | 👁️ Ver      | ✏️ Editar |

✏️ = Puede editar campos D1-D2-D3
👁️ = Solo visualización (read-only)
✅❌ = Puede aprobar o rechazar (pero NO editar contenido)

### Estructura de escalation_path

```json
{
  "issue_users": [
    1,   // [0] = Emisor/Creador (Adrian Salazar)
    2,   // [1] = Aprobador 1 (Robert Robert)
    6,   // [2] = Aprobador 2 (Quality Analyst)
    1    // [3] = Aprobador 3 (Adrian Salazar)
  ],
  "countermeasure_users": [...],
  "confirmation_users": [...]
}
```

**IMPORTANTE**: El elemento [0] de issue_users SIEMPRE debe ser el creador
del reporte. Los índices [1], [2], [3] son los aprobadores secuenciales.

## 5. ENDPOINTS IMPLEMENTADOS
================================================================================

### Backend - Sequential Approval Endpoints

**Archivo**: backend/endpoints/sequentialApprovalEndpoints.js

#### 1. Enviar a Aprobación
```
POST /api/8d/reports/:reportId/d123/send-to-approval

Request Body: (vacío)

Response (éxito):
{
  "success": true,
  "message": "Report sent to Approver 1",
  "new_status": "pending_approval_1",
  "current_step": 1
}

Response (error - ya está en aprobación):
{
  "error": "Report is not in draft status"
}
```

**Lógica**:
- Verifica que el reporte esté en draft
- Verifica que el usuario sea el creador
- Actualiza: d1_d2_d3_approval_status = 'pending_approval_1'
- Actualiza: current_approval_step = 1
- Actualiza: approval_1_status = 'pending'

#### 2. Aprobar
```
POST /api/8d/reports/:reportId/d123/approve

Request Body:
{
  "comments": "Optional approval comments"
}

Response (éxito - pasa al siguiente):
{
  "success": true,
  "message": "D1-D2-D3 approved at step 1. Moving to Approver 2.",
  "new_status": "pending_approval_2",
  "current_step": 2
}

Response (éxito - aprobación final):
{
  "success": true,
  "message": "D1-D2-D3 fully approved! All 3 approvers completed.",
  "new_status": "approved",
  "current_step": 3
}
```

**Lógica**:
- Verifica estado actual sea pending_approval_X
- Verifica que usuario sea el aprobador correcto (escalation_path)
- Registra: approval_X_status = 'approved'
- Registra: approval_X_by = userId
- Registra: approval_X_at = NOW()
- Registra: approval_X_comments = comments
- Si step < 3: Avanza al siguiente step
- Si step == 3: Marca como fully approved

#### 3. Rechazar
```
POST /api/8d/reports/:reportId/d123/reject

Request Body:
{
  "comments": "REQUIRED rejection reason"
}

Response (éxito):
{
  "success": true,
  "message": "D1-D2-D3 rejected at step 1. Returned to creator for corrections.",
  "new_status": "rejected_by_a1",
  "current_step": 0
}

Response (error - falta comentario):
{
  "error": "Comments are required when rejecting"
}
```

**Lógica**:
- Verifica que comments no esté vacío (OBLIGATORIO)
- Registra: approval_X_status = 'rejected'
- Registra: approval_X_by, approval_X_at, approval_X_comments
- Actualiza: d1_d2_d3_approval_status = 'rejected_by_aX'
- Actualiza: current_approval_step = 0 (regresa al creador)

## 7. CASOS DE PRUEBA VALIDADOS
================================================================================

### Caso 1: Flujo de Aprobación Completo (Happy Path)
✅ Adrian (Emisor) crea reporte → estado: draft
✅ Adrian envía a aprobación → estado: pending_approval_1
✅ Campos D1-D2-D3 se bloquean inmediatamente para Adrian
✅ Robert (Aprobador 1) ve botones de aprobar/rechazar
✅ Robert aprueba → estado: pending_approval_2
✅ Robert ya NO ve botones (solo Quality Analyst los ve)
✅ Quality Analyst (Aprobador 2) aprueba → estado: pending_approval_3
✅ Adrian (Aprobador 3) aprueba → estado: approved
✅ Todos ven el reporte como read-only (excepto Admin)

### Caso 2: Flujo de Rechazo y Corrección
✅ Adrian envía a aprobación → pending_approval_1
✅ Robert rechaza con comentarios "TEST rechazo" → rejected_by_a1
✅ Robert ve el reporte en read-only (no puede editar)
✅ Robert NO ve botones de aprobar/rechazar después del rechazo
✅ Adrian ve campos desbloqueados para editar
✅ Adrian ve comentarios de rechazo en UI
✅ Adrian corrige y reenvía → pending_approval_1
✅ Proceso reinicia desde Aprobador 1

### Caso 3: Bloqueo Granular de Aprobadores
✅ Reporte en pending_approval_1
✅ Robert (Aprobador 1) ve:
   - Responsable Principal: 🔒 LOCKED
   - Aprobador 1 (él mismo): 🔒 LOCKED
   - Aprobador 2: 🔓 UNLOCKED (puede cambiar)
   - Aprobador 3: 🔓 UNLOCKED (puede cambiar)

### Caso 4: Historial de Trazabilidad
✅ Tab "Historial" siempre visible
✅ Muestra todos los eventos cronológicamente
✅ Incluye nombre, puesto, fecha/hora de cada acción
✅ Muestra comentarios de rechazo
✅ Indica estado actual del proceso

### Caso 5: Protección contra Doble-Clic
✅ Usuario hace clic en "Confirmar Rechazo"
✅ Si intenta clic duplicado, se ignora
✅ Solo aparece UN mensaje de éxito
✅ Console log muestra: "⚠️ Ya hay una operación en proceso"

### Caso 6: Permisos de Administrador
✅ Admin puede editar D1-D2-D3 en cualquier estado
✅ Admin puede ver y modificar independientemente del flujo
✅ Útil para correcciones de emergencia o auditorías

## 11. LECCIONES APRENDIDAS
================================================================================

1. **Sincronización de Estado**: Siempre actualizar estado local de React
   después de llamadas API exitosas para evitar problemas de UI stale.

2. **Prevención de Doble-Clic**: Agregar verificaciones de loading state
   al inicio de handlers para prevenir race conditions.

3. **Compatibilidad con Sistemas Existentes**: Al agregar funcionalidad nueva,
   mantener compatibilidad con sistema viejo usando condicionales.

4. **Rol vs Usuario**: Distinguir claramente entre:
   - Creador del reporte (Emisor)
   - Trabajador asignado (Primary)
   - Aprobadores (Reviewers)

5. **Administrador Override**: Siempre implementar bypass para administradores
   en casos de emergencia, pero documentar claramente para auditoría.

6. **Trazabilidad**: El historial de cambios es CRÍTICO para:
   - Auditorías de calidad (ISO 9001, TS 16949)
   - Resolución de disputas
   - Análisis de tiempos de aprobación
   - Training de nuevos usuarios
