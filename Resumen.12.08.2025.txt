PROBLEMA INICIAL:

- Se perdía trazabilidad

CAUSA RAÍZ IDENTIFICADA:

- Causa: mapD3MfgToBackend en eightDService.js enviaba approval_step en cada guardado
- Los campos de aprobación deben manejarse SOLO por endpoints de aprobación

SOLUCIONES IMPLEMENTADAS:

A) Frontend - D3MFG.js:

   1. Lógica de bloqueo mejorada (líneas 79-87):
      ```javascript
      const isFormBlocked = data?.d3MfgStatus === 'under_review' ||
                            data?.d3MfgStatus === 'approved' ||
                            (data?.d3MfgCurrentApprovalStep >= 1 && data?.d3MfgCurrentApprovalStep <= 3) ||
                            data?.d3MfgCurrentApprovalStep === 4 ||
                            !isPrimaryUser(); // CRÍTICO: Solo el primario puede editar
      ```

   2. Concepto de effectiveStep implementado:
      - Cuando d3MfgStatus='under_review' pero currentApprovalStep=0 → asume step=1
      - Aplicado en 3 funciones:
        * isCurrentApprover() - líneas 43-61
        * currentUserInProcess - líneas 92-119
        * Cinta de estado - líneas 1084-1094

   3. Separación de guardado normal vs aprobación (líneas 314-369):
      - handleSendToApproval ahora hace 2 operaciones:
        1. Guarda datos del formulario vía onDataUpdate(formData)
        2. Envía estado de aprobación vía PUT directo al backend

   4. Condición de botones corregida (línea 2370):
      - Antes: isInApprovalState() && isCurrentApprover()
      - Ahora: data?.d3MfgStatus === 'under_review' && isCurrentApprover()
      - Usa status (confiable) en lugar de step (corrupto)

CONCEPTOS TÉCNICOS CLAVE PARA ENTENDER EL CÓDIGO
================================================================================

1. EFFECTIVE STEP:
   - Variable calculada que corrige el step corrupto
   - Fórmula: si (status='under_review' Y step=0) entonces step=1, sino usar step real
   - Usado en validaciones, UI y backend
   - Solución al problema de corrupción de datos

2. SEPARACIÓN DE CONCERNS:
   - Datos de formulario → manejados por onDataUpdate + mapD3MfgToBackend
   - Estado de aprobación → manejado SOLO por endpoints de aprobación
   - NUNCA mezclar: cada uno tiene su responsabilidad

3. BLOQUEO MULTINIVEL:
   - Nivel 1: Status (under_review/approved) = bloqueado para todos
   - Nivel 2: Usuario (si no eres primario) = bloqueado siempre
   - Nivel 3: Aprobadores nunca editan, solo aprueban/rechazan
   - Resultado: Solo primario edita, solo en draft

4. SNAKE_CASE ↔ CAMELCASE:
   - Backend usa snake_case (d3_mfg_status)
   - Frontend usa camelCase (d3MfgStatus)
   - Transformación automática en eightDService.js
   - transformToCamelCase en línea 359
